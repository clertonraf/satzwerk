## Pain Points & Challenges

### 1. Too Many Review Rounds (6 rounds for a single feature)
**Root Cause**: The initial implementation and early fix rounds did not proactively consider the full set of edge cases a reviewer would flag. Each round fixed the reported issue but introduced new surface area (e.g., fixing loop bounds exposed the jagged-column issue, which exposed the tooltip issue).  
**Impact**: ~6 additional push/wait/fix cycles; user frustration  
**Frequency**: Every PR in this project follows multi-round review  
**Prevention Strategy**: Use rubber-duck agent critique *before* the first push to simulate reviewer comments; use it again after each significant fix

### 2. CI Failures on Pushed Code
**Failure 1 — detekt `MaxLineLength`** (`d51d7c2`):  
`AnalyticsHandler.kt:23` was 122 chars. ktlint passed but detekt caught it. Local `./gradlew ktlintCheck` was run but not `./gradlew detekt`.  
**Root Cause**: Treating ktlint and detekt as interchangeable. They are not — ktlint handles style, detekt handles static analysis including line length.  
**Failure 2 — Missing `BigDecimal` import** (`ac67dfb`):  
When adding the `assertEquals` import, `ktlintFormat` reorganised imports and the edit replaced `import java.math.BigDecimal` instead of inserting beside it.  
**Root Cause**: `ktlintFormat` silently reorders the import block; subsequent `edit` operations targeting by line content can collide.  
**Combined Impact**: 2 broken CI runs, 2 extra commits, extra wait cycles  
**Prevention Strategy**:  
- Always run `./gradlew ktlintCheck detekt --no-daemon` together before every push  
- After any import restructuring, verify compilation locally before pushing

### 3. Fix-Induced Regression (Missing Import)
The BigDecimal import removal is a textbook example of a narrow edit causing a non-local breakage. The file compiled fine locally because Gradle cached the previous compiled output; only CI (clean build) caught it.  
**Root Cause**: Not running `./gradlew compileTestKotlin` (or `test`) locally after the import change  
**Prevention Strategy**: After any backend file edit, run the full test suite locally, not just linters

## Patterns for Future Reference

### Successful Patterns to Replicate

1. **Raw API comment fetch**: Use `gh api repos/{owner}/{repo}/pulls/{n}/comments --jq` for inline review detail instead of `gh pr view --comments`. The latter only shows summaries.

2. **UTC-safe date arithmetic in JS**: When subtracting months, use `new Date(Date.UTC(y, targetMonth+1, 0)).getUTCDate()` to clamp day-of-month. Never use `Date.UTC(y, m-N, d)` directly.

3. **Grid alignment**: Align start back to Monday (`dayOfWeek === 0 ? -6 : 1 - dayOfWeek`) and end forward to Sunday (`endDayOfWeek === 0 ? 0 : 7 - endDayOfWeek`) to guarantee `totalDays % 7 === 0`.

### Anti-Patterns to Avoid

1. **Running ktlint without detekt**: They catch different things. Always run both. Alias: `./gradlew ktlintCheck detekt`.

2. **Editing imports after ktlintFormat runs**: The formatter reorders the entire import block. Subsequent line-targeted `edit` calls can collide and silently drop imports. Always verify with `compileTestKotlin`.

3. **Skipping rubber-duck before push**: Reviewer simulation after implementation is cheap; reviewer simulation after 6 push/review cycles is expensive. Run rubber-duck before the first push.
